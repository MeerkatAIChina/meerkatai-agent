# v0.1.2 设计文档

## skill 快照随包内置，GitHub 降级为更新通道（issue #6）

> 需求依据：[需求描述.md](./需求描述.md) Bug 一节
> 调研结论：[需求调研.md](./需求调研.md)「Bug」一节
> 架构决策：[ADR.md](./ADR.md) ADR-003 / ADR-004
> 设计评审：2026-08-20 分节评审通过（1-A 本地直读 + 2-A upstreamUrl + D 拆分）

### 概述

桌面版首启时 web-ui 启动任务无条件向 GitHub 克隆 skill pack，在「首启 + 无代理/无直连」窗口必然失败：4 次退避重试白烧约 100 秒、日志噪音大、首个会话 TRIZ 技能缺失。同时代码实证发现：即使种子改指本地路径，现有 fetcher 对本地目录也是 `git clone`——无 git 客户机器上本地导入同样失败（客户日志的 `spawn git ENOENT` 即源于此）。

本设计落实 issue 方案 A：**构建期把 GitHub 仓库物化为快照随包内置，首启零网络零 git 依赖；GitHub 降级为更新通道（启动单次 + 手动触发，尽力而为）**。配套小项 D 拆分：启动清单技能包状态行本期做；设置页「重新同步」按钮并入优化 2（设置页入口）。

三个前置决策（已拍板）：

1. **本地目录直读**：core fetcher 对带元数据标记的本地快照跳过 git，直接读目录（否决随包 portable git）。
2. **`upstreamUrl` 双地址身份**：本地路径做 `url`（身份稳定），GitHub 地址存 `upstreamUrl`，sync 走 upstream（否决 web-ui 编排 PATCH 往返、否决砍掉在线更新）。
3. **D 拆分**：设置页「重新同步」依赖优化 2 的设置页入口，本期只做启动清单状态行；现成端点 `/api/desktop/skill-packs/retry` 留给优化 2 挂按钮。

### 第一节：整体架构

一条主线：**构建期把 GitHub 仓库物化成快照 → 运行时首启只读本地快照 → GitHub 退为可选更新通道**。

```
构建期（stage-payload.sh / stage-payload.ps1）
  skillpacks.conf（唯一仓库清单源）
    → git clone --depth 1 → payload/skillpacks/<slug>/（去 .git，写 .skillpack-meta.json）
    → 生成 payload/config/seeds/skillpacks.json（相对路径 + upstreamUrl + local:true）

首启/每次启动（web-ui server）
  读种子 → 相对路径解析为 payload 内绝对路径
    → 注册/匹配/迁移 pack（url=本地路径，upstreamUrl=GitHub）
    → 本地导入（core fetcher 直读快照，无 git 无网络，必成功）
    → 后台单次 POST /sync {onlyIfUpdate:true}（尽力而为，失败一行日志）

更新通道（core）
  upstreamUrl 存在时 sync/resolveRef 走 GitHub；桌面无周期 tick（现状即如此）
```

触点清单：

| 层 | 触点 | 改动量 |
|---|---|---|
| 构建 | `stage-payload.sh`、`stage-payload.ps1` | 各加快照克隆 + 种子生成一段 |
| core | `pack-fetcher.ts`、`skill-pack-store.ts`、`skill-packs.ts`（routes）、`app-skills.ts`、`skill-sync-engine.ts` | 见第三节 |
| web-ui | `plugins/web-ui/server/index.ts` 启动任务重构 + 状态端点 | 第四节 |
| desktop | `ui/index.html` 加技能包行；`src-tauri/src/main.rs` 加一个只读 command | 第五节 |
| Tauri | `main.rs` 新增 `skillpacks_status` 只读 command（ureq 转发，无新依赖） | ~15 行 Rust |

### 第二节：构建期快照

- `deploy/layers/meerkat/skillpacks.conf` 升为**唯一仓库清单源**（桌面种子与快照都从它生成，消除双胞胎漂移）。
- `stage-payload.sh` 与 `stage-payload.ps1` **双胞胎同步修改**：每个仓库 `git clone --depth 1` 到 `payload/skillpacks/<slug>/`（slug = 仓库名，如 `meerkat-skills-triz`），`git rev-parse HEAD` 记录 commit 后**删除 `.git`**，写入 `.skillpack-meta.json`：

  ```json
  {
    "upstreamUrl": "https://github.com/MeerkatAIChina/meerkat-skills-triz.git",
    "ref": "main",
    "commit": "<sha>",
    "snapshotAt": "<ISO 时间>"
  }
  ```

- **快照种子由构建生成** `payload/config/seeds/skillpacks.json`：

  ```json
  {
    "packs": [
      {
        "name": "meerkat-skills-triz",
        "url": "skillpacks/meerkat-skills-triz",
        "upstreamUrl": "https://github.com/MeerkatAIChina/meerkat-skills-triz.git",
        "ref": "main",
        "local": true
      }
    ]
  }
  ```

  取代手工维护的 `desktop/seeds/skillpacks.json`（删除）。构建机与 CI 均有网络，克隆零成本。
- clone 失败 → 构建直接失败（`set -euo pipefail` 天然保证），宁缺毋滥，杜绝发包后才发现快照没打进去。
- 交付确定性：客户安装到的技能内容 = 构建时快照，commit 可追溯（与 rootfs `fingerprint.txt` 同模式）。

### 第三节：core 改动

1. **fetcher 本地直读**（`src/skills/pack-fetcher.ts`）：`fetch` 与 `resolveRef` 中，当 `permitsLocal(pack)` 且路径为本地路径且**存在 `.skillpack-meta.json`** 时——跳过 git：`fetch` 直接 `readTree`（maxFiles/maxTotalBytes 护栏不变），commit 取元数据；`resolveRef` 直接返回元数据 commit。**无元数据的本地路径保持 legacy `git clone` 行为逐字节不变**（dev 流与 bare repo 场景不回归，meta 文件是显式 opt-in 标记）。元数据缺失 commit 字段或 JSON 损坏 → 显式报错，不静默兜底。
2. **`SkillPack.upstreamUrl?: string`**（`src/skills/skill-pack-store.ts`）：软字段；store 基于 `DurableMap<SkillPack>` 整条 JSON 存取，**无需 SQLite 迁移**。
3. **routes**（`src/api/routes/skill-packs.ts`）：
   - register 接受 `upstreamUrl`（格式校验：https、无内嵌凭据，否则 400）；
   - patch 接受 `upstreamUrl`，并**放开 `local` 字段**——`patchPack` 现有白名单（`skill-packs.ts:159-170`：ref/url/trustTier/syncMode/subset/config）不能置 `local`，不放开则 v0.1.1 老客户升级后 pack 迁移不掉。守卫：仅当 core 以 `ALLOW_LOCAL_SKILL_PACKS=1` 运行**且**最终生效 url 为本地路径时才允许置 `local:true`，否则 400。
4. **app-skills**（`src/api/app-skills.ts`）：
   - `POST /sync` 接受 `{onlyIfUpdate:true}`——先 `resolveRef`（有 upstreamUrl 走 upstream），`lastImport.status==="ok"` 且 HEAD 一致则返回 `{skipped:true}`，不 clone；否则 reconcile。
   - reconcile 的 fetch 源：`reconcilePack` 增加 fetch 源参数——`importSkillPack` 传 `url`（本地快照），`syncSkillPack` 传 `upstreamUrl ?? url`；走 upstream 时原有 https/无凭据/SSRF/代理校验逐字节不变，只是源地址字段换了。注意：`skillPackSourceIdentity` 比对（`app-skills.ts:122`）仍用 store 里的原始 pack，不参与源切换。
   - **sync 抓取失败时 `recordImport` 保留上一个成功 commit**（现 `reconcilePack` 失败路径写 `commit: pack.ref` 即 `"main"`（`app-skills.ts:113`），会把 `updateAvailable` 的比对基准毁掉；改为 `pack.lastImport?.commit ?? pack.ref`）。
5. **sync-engine**（`src/skills/skill-sync-engine.ts`）：`resolveRef`/`fetch` 支持 upstream 源（有 upstreamUrl 时比对与抓取走 GitHub）。周期 tick 无需任何改造——`SKILL_SYNC_POLL_MS` 默认就是 0（`config.ts:458`），`wiring.ts:1495` 仅在 `> 0` 时才 `start`，**桌面版今天就没有周期 tick**，不新增 env。桌面更新时机 = 启动单次 `onlyIfUpdate` + 手动重同步。

### 第四节：web-ui 启动任务重构

`maybeStartSkillPacks`/`ensureSkillPacks`（`plugins/web-ui/server/index.ts:919-1035`）重写为四段：

1. **解析**：种子相对 url → 由 `MEERKAT_SEEDS_DIR`（恒为 `payload/config/seeds`）推 payload 根（`join(SEEDS_DIR, "..", "..")`），拼出快照绝对路径；同时读 `.skillpack-meta.json` 取快照 commit。`isLocalRepoPath` 只认绝对路径——相对路径解析在 web-ui 侧完成，**core 永远只见绝对路径**。
2. **注册/匹配/迁移**：匹配规则 = `url === 种子.url || url === 种子.upstreamUrl || upstreamUrl === 种子.upstreamUrl`。命中老版本 GitHub pack（`url === 种子.upstreamUrl` 且无 upstreamUrl）→ PATCH 迁移为「url=本地绝对路径 + upstreamUrl=GitHub + local:true」，pack id 与已导入技能全部保留；未命中 → 注册（带 `upstreamUrl`、`allowLocal:true`）。
3. **本地导入**：`lastImport.status==="ok" && lastImport.commit === 快照commit` → 跳过（每次启动不再重复导入）；否则 import。**本地导入失败不做退避重试**——直读失败就是快照损坏，重试无意义，直接置 degraded。
4. **更新通道**：`POST /sync {onlyIfUpdate:true}` 单次调用，失败一行 `console.warn` 完事。原 4 次 × 21s 退避轰炸整体删除。`/api/desktop/skill-packs/retry` 端点保留，语义变为重跑此流程（留给优化 2 的设置页按钮挂）。

### 第五节：可见性（配套小项 D 前半）

- web-ui 新增 `GET /api/desktop/skill-packs/status`（DESKTOP 门控，走 `/api/*` 统一认证闸门——DESKTOP 下认 `x-portal-identity`，对齐现有 `/api/desktop/*` 端点如 retry）：返回每包 `{name, phase: pending|importing|ready|degraded, detail?, updateAvailable?}`。状态来源两张牌：流程在跑时由第四节流程就地维护（进程内存态）；**流程未在运行时（web-ui 重启后、优化 2 设置页打开时）从 store 就地推导**——`lastImport.status==="ok"` → ready；`error` 但 `commit` 等于快照 commit → ready（导入本身完好、仅 upstream 检查失败，对齐错误矩阵「无网绿灯」）；其余非 ok（从未导入、快照已变更、register/import 失败）→ pending 而非 degraded——status 轮询自身即触发 `maybeStartSkillPacks`，由启动流程仲裁后就地写 mem 呈现 ready/degraded，真 degraded 必经流程确认，不会被推导锁存（该临时状态每次启动重跑、可从 `lastImport`/`updateAvailable` 重导，符合「Durable by default」）。
- splash 页（`deploy/layers/meerkat/desktop/ui/index.html`）加「技能包」行：拿到 ports 后每 2s 经 Tauri command `invoke("skillpacks_status")` 轮询，直至 ready/degraded 后停止轮询；severity 恒黄灯，`maybeEnter()` **不等待**技能包行（对齐沙箱行降级纪律：黄灯可进主界面，能力暂时退化）。
- **Rust 侧改动仅为一个只读 command**（`main.rs` 的 `skillpacks_status`，用已在依赖里的 ureq 转发 GET `/api/desktop/skill-packs/status`，无新 crate）。不复用 `component-ready`/`component-failed` 事件，因为导入编排发生在 web-ui 进程内，Tauri 无从感知；splash 页是 tauri 源、web-ui 无 CORS 头，浏览器直连取数走不通，Tauri command 中转是最小缝（沙箱行 `wsl2_status` 同一先例）。
- 设置页「重新同步」按钮：本期不做，并入优化 2。

### 第六节：错误处理矩阵

| 场景 | 行为 |
|---|---|
| 快照缺失/元数据损坏（安装包问题） | 本地导入显式报错 → 清单黄灯「技能包不可用」+ 日志；**不尝试 GitHub 兜底**（快照是构建物，坏了就是打包事故，兜底会掩盖打包事故） |
| 无 git 机器 | 全链路不 spawn git（直读通道），零影响——顺带修复 `spawn git ENOENT` |
| 无网/无代理 | 本地导入成功；upstream `onlyIfUpdate` 一次失败一行 warn；清单绿灯（技能可用） |
| 代理已配 | upstream 走 `SKILL_PACK_GIT_PROXY`（v0.1 ADR-008 + v0.1.2 ADR-001 路径不变） |
| upstream 有新提交 | 启动时增量同步落 SQLite；`updateAvailable` 语义保持 |
| upstream sync 中途进程死亡 | `recordImport` 保留旧 commit，下次启动重试（天然幂等） |

### 第八节：ADR 摘要

- **ADR-003 本地快照直读通道**：meta 文件为显式 opt-in 标记，直读仅认 meta 标记的快照目录；信任边界：meta 文件随包签名交付。内核缝改动，guardrails 不变。
- **ADR-004 `upstreamUrl` 双地址身份 + 更新时机语义**：本地快照为身份与首启源，GitHub 为更新通道；patch 放开 `local` 守卫支撑老版本迁移；桌面更新时机 = 启动单次 + 手动。

（完整背景/被否决方案/后果见 [ADR.md](./ADR.md)。）

### 第九节：不做

- 设置页「重新同步」按钮（并入优化 2，端点已备好）。
- **dev 流（`meerkat-local-up.sh`）保持 GitHub 直连注册不变**：该脚本（`scripts/meerkat-local-up.sh:80-93`）同样消费 `skillpacks.conf`，但直接用 GitHub url 注册 + import（无 `local`、无 `upstreamUrl`），不依赖种子文件，不受手工种子删除影响，且与桌面运行时数据目录隔离。注意其注册出的 pack 恰好命中第四节的「老版本 GitHub pack」迁移规则——这是预期行为而非缺陷。是否把 local-up 也切到快照通道，留作后续。

- 快照损坏时的 GitHub 兜底——见错误矩阵，刻意不做。

## UI 界面 i18n 中文化（需求 2.1 + 2.2 品牌替换）

> 需求依据：[需求描述.md](./需求描述.md) 需求 2.1 / 2.2
> 调研结论：[需求调研.md](./需求调研.md)「需求二：i18n 国际化」
> 设计评审：2026-08-23 两轮评审。第一轮 6 条（setTranslations 裸替崩溃、localStorage 条件写入矛盾、17 条必需 key 清单、ADR 义务、测试断言口径、品牌范围）已全部并入；第二轮 4 条（tr() 防崩 helper、测试影响原则性口径、品牌三中枢点名、零注释提醒）已全部并入
> 拍板结论：机制 = mini-lit 同源方案；语言策略 = 硬默认中文、不做切换入口；admin 全量纳入本期；zh 字典放 web-ui 插件内独立 locale 文件

### 第一节：机制与总体结构（一份字典，三处注入）

**唯一字典** `plugins/web-ui/src/locale/zh-cn.ts`，key = 英文原文，覆盖三类内容：

| 内容 | key 数量级 | 说明 |
|---|---|---|
| mini-lit 必需 key | **17 条** | 以源码 `defaultEnglish` 为准：`*`、Copy、Copy code、Copied!、Download、Close、Preview、Code、Loading...、Select an option、Mode 1、Mode 2、Required、Optional、Input Required、Cancel、Confirm——缺失会导致 mini-lit 组件报错 |
| pi-web-ui 附件链路 | ~20-30 条 | 只翻 qm 实际触达的 `loadAttachment` 相关消息，不是全量 201 条 |
| qm 自有文案 | ~1000-1200 条 | 27 个文件逐串包裹后自然汇集 |

**boot 注入**（`plugins/web-ui/src/main.ts` 最早期，先于任何渲染）：

```ts
localStorage.setItem("language", "zh");                        // 无条件覆盖，硬默认中文
setTranslations({ ...getTranslations(), zh: ZH_CN });          // 展开合并，禁止裸替
```

两个反直觉点（评审实证，均为 mini-lit 源码行为）：

1. **`setTranslations` 是整体替换不是合并**（`translations = customTranslations`）。裸写 `setTranslations({zh: ZH_CN})` 会清掉内置 en/de 字典；而 `getCurrentLanguage()` 在 localStorage 写入前的窗口期会回退浏览器语言 `"en"`，此时 `translations["en"]` 为 undefined → `i18n()` 内取下标直接 TypeError。jsdom 测试环境（无 localStorage 预置）稳定踩中。必须展开合并：`{ ...getTranslations(), zh: ZH_CN }`。
2. **不能「若未设置才写 zh」**：`getCurrentLanguage()` 优先读 localStorage，老用户机器上若存过 `"en"` 就永远停在英文，「默认就是中文」不成立。boot 时无条件写入 `"zh"`（与拍板一致：无切换入口，localStorage 里没有其他合法来源）。
3. **裸 Node/无 storage 环境下 `i18n()` 本身会抛 ReferenceError**（实测 Node v24.15.0 裸环境 `typeof localStorage === "undefined"`；mini-lit 的 `getCurrentLanguage()` 每次调用都读全局 localStorage）。因此组件使用的 `i18n` 必须是 locale 模块的**安全包装版**（try/catch 内部调用，异常回退 key 本身），禁止组件直接 import mini-lit 的 i18n；`tr()` 建于其上。这一处包装同时免疫生产端 storage-disabled 场景（隐私模式/sandboxed iframe 下每次调用抛 SecurityError，是真实存在的桌面 webview 风险）。

**不调 `setLanguage()`**——它内部 `window.location.reload()`，boot 直写 localStorage 即可，无需刷新。

### 第二节：各工作面落点

| 工作面 | 做法 |
|---|---|
| web-ui 27 文件（~1000-1200 条） | 模板文本节点、`title/placeholder/aria-label` 属性、toast/confirm 消息逐处包 `i18n("...")`（一律从 web-ui 的 locale 模块 import 安全包装版，禁止直接 import `@mariozechner/mini-lit` 的 i18n——见第一节反直觉点 3） |
| pi-web-ui 硬编码 throw（5~8 条） | `Failed to process PDF/DOCX/...`、`Unsupported file type` 未走 i18n，在 `composer.ts` 的 `loadAttachment` 调用处 catch 后映射为中文 |

### 第三节：动态拼接串规范

- 含插值的串：字典值用**函数**（mini-lit 源码显式支持：`typeof value === "function"` 时原样返回），如 `"N files selected": (n) => \`已选择 ${n} 个文件\``
- **动态串调用处必须走防崩 helper，禁止裸写 `i18n(key)(n)`**——mini-lit 在 key 未命中时返回 key 字符串本身，再 `(n)` 调用就是 TypeError。两个必踩场景：jsdom 测试（无 zh 字典，所有动态 key 未命中）和生产漏翻（静态串漏翻只回退英文，动态串漏翻是 crash，严重度不对等）。locale 模块统一导出：

```ts
export function tr(key: string): (...args: unknown[]) => string {
  const v = i18n(key);
  return typeof v === "function" ? v : () => String(v);
}
```

调用处 `tr("N files selected")(n)`——未命中时优雅回退英文 key，与静态串行为对齐。
- **禁止按词拼接**（如 `i18n("Delete") + name`），整句作为一个 key——中英文语序不同
- 复数无需机制（中文天然免疫）

## 接入 MCP Server 服务（需求 3，lawaken-memory-dev）

### 概述

桌面版接入 lawaken memory MCP 服务（`https://dev.lawaken.com/api/memory/mcp`，`X-Lawaken-MCP-Key` 自定义头鉴权），让 agent 能召回 lawaken 侧的记忆作为上下文。qm core 有原生 MCP 子系统（`src/mcp/` + admin 路由 + harness 注入），协议与 URL 形态兼容；唯一硬 gap 是 client 不支持自定义认证头。本设计 = core 补 header 单头认证 + 设置页 MCP 配置表单（连带优化 2 回访入口最小版）。

**拍板记录**（Brainstorming 2026-08-24）：

1. **用途定位：只读召回**。server 注册 `readOnly:true`（core 缺省），agent 只读 lawaken 记忆、不写入，安全面最小；写能力后续视联调结果再放开。
2. **认证路线 A：core 加自定义 header 支持**，形态为**单头模式** `{ mode: "header", name, value }`。YAGNI 否决任意字典（`Record<string,string>` 是为「一个调用方都没有的模式」造抽象）；B（lawaken 兼容 Bearer）依赖外部、C（sidecar 改写头）放大运维与安全面，均否决。
3. **上游可贡献形态**：core 实现零 meerkat/lawaken 字样，测试用中性头名（如 `X-Custom-Key`），保留 upstream-pr 送回主仓的选项。
4. **按需配置，不预置**：MCP 接入非全员使用，安装包不带任何 lawaken 配置与 key（无种子、无 key 入包），由交付/运营在客户现场通过设置页配置。
5. **配置入口：设置页 UI 表单**，连带优化 2 最小版（回访入口 + 既有 secret 字段「留空=不修改」脱敏语义）一起做。
6. **方案 1：扩展现有 setup.html 设置页**（对比 SPA 内嵌 Lit 视图与 admin 后台后选定；详见需求调研「需求三」§2-3）。

**钉死项**（方案拍板时固定）：

1. 转发路由照 `registerProviders` 模式：`/api/setup/mcp-servers[/:id]` → core `/v1/admin/mcp-servers`，GET 透传 redact 结果；
2. secret 字段（含新的 `headerValue`）走「留空=保留」语义，与 core PUT 现有行为对齐；
3. 手填场景 `validate:true`（probe 验通才落库）；未来若引入种子预置通道则 `validate:false`；
4. header 模式的 redact 扩展列入内核缝改动清单（随 ADR 一起）。

### 第一节：core 认证扩展（header 单头模式）

**类型与存储**（`src/mcp/mcp-server-store.ts`）
- `McpServerAuthMode` 新增 `"header"`；`McpServer` 新增 `headerName?: string`、`headerValue?: string` 可选字段（DurableMap 整条 JSON 存取，无迁移；存量记录无此字段行为不变）。

**客户端**（`src/mcp/mcp-client.ts`）
- `McpAuth` 新增 `{ mode: "header"; name: string; value: string }`；`authHeaders()` 返回 `{ [name.toLowerCase()]: value }`，与 bearer 互斥（一个 server 一种 auth）。

**路由校验**（`src/api/routes/admin/mcp-servers.ts`）
- `auth === "header"` 时：
  - `headerName` **新建与更新均必填**：必须是合法 HTTP header token（`/^[!#$%&'*+.^_`|~0-9A-Za-z-]+$/`），且**大小写不敏感**地不在保留名单内（`authorization`、`host`、`content-type`、`accept`、`content-length`、`connection`、`transfer-encoding`）。`authorization` 是真正必须拦的（`authHeaders()` 展开在前，漏拦会直接覆盖 Bearer 头）；`host`/`content-length`/`connection`/`transfer-encoding` 属 fetch 管理的 hop-by-hop 头，拦上是正确防御。
  - 不对称的 preempt 说明：`headerName` 必填而 `headerValue` 留空=保留——因为 name 不是 secret、redact 明文返回、前端可预填，client 拼装请求时缺 name 无法工作；这与 `client-credentials` 的 `clientId` 留空=保留不同（clientId 仅换 token 时使用，core 持有旧值即可），两条规则各有依据，不是不一致。
  - `headerValue` 新建必填、更新**留空=保留**（逐字对齐现有 `b.bearerToken ? b.bearerToken : existing?.bearerToken` 写法）。auth 切换时旧 secret 字段被丢弃（条件 spread 不带即清）的现有语义对 header 字段同样适用——切换 auth 模式即清空旧 secret，测试钉住。
- `redact()` 扩展：签名改为 `Omit<McpServer, "bearerToken" | "clientSecret" | "headerValue">`，返回增加 `hasHeaderValue`，与既有 `hasXxx` 同构。
- `mcp-tool-service.ts` 的 `authOf()` 增加 header 分支映射。

**ADR**：`ADR.md` 新增一条，决策链：「需求鉴权方式为自定义头 → B 依赖外部、C 放大运维与安全面 → 选 A 的 header 单头模式（YAGNI 否决任意字典）」，内核缝清单含 redact 扩展（钉死项 4）。

### 第二节：web-ui server 转发路由

照 `registerProviders` 模式，DESKTOP-only + cookie 鉴权（非 DESKTOP 404）：

| 路由 | 行为 |
|---|---|
| `GET /api/setup/mcp-servers` | 转发 core `GET /v1/admin/mcp-servers`，**透传 redact 结果**（secret 不回前端，只回 `hasXxx` 标志）+ 工具清单 |
| `PUT /api/setup/mcp-servers/:id` | 转发 core PUT；secret 字段前端留空 → 转发时**剥离该字段**（由 core 执行留空=保留）；`validate` 缺省 `true`（手填场景 probe 验通才落库） |
| `DELETE /api/setup/mcp-servers/:id` | 转发 core DELETE |

- **web-ui 不做 id 预校验**：`isValidMcpServerId` 在 core，plugin 不能 import core，预校验 = 抄正则副本且与 core 400 message 透传无行为差异。core 单点校验、web-ui 透传。
- **「probe 失败 = 保存失败」是刻意的 fail-closed 姿态**：`validate:true` 缺省意味着 lawaken 临时不可达时连改 name/readOnly 都保存不了。从 core 继承、手填场景合理（防存下打不通的配置），不是 bug。
- 错误透传同构 `registerProviders`：core 400（含 `unreachable`）原样透 message，其余 5xx 归 502。

### 第三节：setup.html 表单 + SPA 回访入口（优化 2 最小版）

**setup.html 新增「MCP 服务」区块**（置于现有配置区块之后）

- **列表区**：展示已注册 server（`GET /api/setup/mcp-servers` 的 redact 结果）：id、name、url、auth 模式、headerName（明文）、密钥状态（`hasXxx` → 「已配置/未配置」）、工具数、enabled/readOnly；每行「编辑」「删除」。
- **编辑/新增表单**：
  - `id`：新建可填（提示规则：小写字母开头，小写+数字+连字符，2-40 位），**编辑时禁用**（id 即身份，且会成为工具名前缀）；
  - `name`、`url`：常规文本框；
  - `auth`：下拉三选一 `none / bearer / header`（`client-credentials` 为服务间 OAuth 场景，桌面手填用不上，**表单不暴露**，core 能力保留）；
  - 按 auth 动态显隐：`bearer` → token 框；`header` → headerName + headerValue 两框；
  - secret 框 placeholder 按 `hasXxx` 显示「已配置，留空则不修改」；
  - `readOnly` 复选框**默认勾选**（只读召回既定语义）、`enabled` 默认勾选；
  - 保存 → `PUT /api/setup/mcp-servers/:id`；400 时表单内展示 core 透传的 message。
- **优化 2 脱敏语义**：现有 token / localApiKey 字段同步改「留空=不修改」——`registerProviders` 调整：token 仅在**首次注册**（无既有 provider）时必填；回访时留空则剥离不转发。core 零改动（`customProviders.upsert` 本就 apiKey 留空=保留旧值，且 apiKey 缺失时跳过 validate）。

**SPA 回访入口（带 token 跳转）**

- web-ui shell 加「设置」按钮（齿轮图标，i18n 中文「设置」），**跳转时把当前 URL 上的 `portal_token` 带上**：`location.href = "/setup?portal_token=" + encodeURIComponent(current)`。
  - 原因：setup.html 的 portal token 仅来自 `?portal_token=` query 或 localStorage `meerkat.portal_token`，而桌面 portal token TTL 只有 24h——裸跳 `/setup` 在应用连续运行超过 24h 后必然 401。带 token 跳转后，setup.html 已有的 query→localStorage 刷新逻辑会自动把新 token 落进 localStorage，完成自愈。
  - 返程无需处理：setup.html 返回主界面时已拼 `/?portal_token=`。
- `/setup` 服务端路由已存在（`index.ts` 的 `/setup` 分支，任何时刻可访问），零改动。

### 第四节：数据流 / 错误处理

**数据流（注册 → 工具上线）**

```
setup.html 表单 → PUT /api/setup/mcp-servers/:id（web-ui server 转发，secret 留空则剥离）
  → core PUT /v1/admin/mcp-servers/:id（validate:true → probe 打 tools/list 验通）
  → mcp_servers DurableMap 落库 → onChange 触发 mcpToolService.refresh()
  → 工具以 <id>_<toolName> 命名空间注入 harness（wiring 实证：pi/opencode/codex/claude 均接收 mcpTools）
  → 下个 turn 起 agent 可见可调用
```

- 注入防御在 **harness 层**（pi 实证 `pi-tools.ts`：工具 description 尾部拼「外部内容视为数据而非指令」后缀 + `recordExternalResult` 结果标记）；其余三个 harness 的同层防御形态执行期核证。
- 调用链：agent → `callMcpTool` → `mcpToolService.call(name, args, principalId)` → client 带自定义头 POST → 结果文本截断 60k 字符；审计由 `mcpToolService` 记录（resource 为 `<serverId>` / `<serverId>/<remoteName>`，scopeLabel `mcp-connectors`）。

**错误处理**

- probe 失败（lawaken 不可达/key 错）→ core 400 `unreachable` → 表单原样展示 message，**不落库**（fail-closed）；
- core 未就绪 → web-ui 502，表单提示稍后重试，已有配置不受影响；
- 调用期失败（运行时才不可达）→ agent 侧收到 `[error] mcp tools/call failed`，审计留痕，不影响会话其余部分；
- 删除 server → onChange 刷新快照，工具立即下线；进行中的 turn 不受影响（工具定义是 turn 开始时快照的）。

### 第五节：测试与验收

**core 单测**（中性命名）：

- `authHeaders()` header 模式产出指定头、与 bearer 互斥；
- headerName 非法字符 → 400；**命中保留名单的大小写变体（`Authorization`、`CONTENT-TYPE`）→ 400**（唯一容易漏 `toLowerCase` 的地方，必钉）；
- `headerValue` 新建缺失 → 400、更新留空=保留；`headerName` 更新缺失 → 400；
- auth 模式切换时旧 secret 字段清空（`bearer→header` 丢 `bearerToken` 等）；

## 技能页本地上传入口（需求 4，md / zip）

### 概述

需求原文：[需求描述.md](./需求描述.md) 需求 4；调研：[需求调研.md](./需求调研.md)「需求四」；背景：issue [#17](https://github.com/MeerkatAIChina/meerkatai-agent/issues/17)。Skills 页右上角加「本地上传」按钮，支持 md 单/批量与 zip 批量两类文件，混选一次上传。

**零 core 改动**：md 走 `POST/PUT /v1/skills`，zip 走 local skill pack（`allowLocal` 受控通道，桌面已由 proc.rs:261 固定注入 `ALLOW_LOCAL_SKILL_PACKS=1`）。全部改动落在 plugins/web-ui（server 新模块 + Skills 页 UI + zh-cn 词条）。

**拍板记录（偏离需求原文一处）**：需求描述写 zip「客户端解压校验」，本设计改为 **server 侧解压**——解析/校验规则只在 server 侧一份副本，前端保持哑（选文件 + 渲染预览 + 确认），避免前后端两套规则漂移出现「预览说行、注册 400」。jszip ^3.10.1 是 plugins/web-ui 的 dependency（package.json:27），Node 侧可用。

**对 Brainstorming 拍板的一处实证修正**：Q3 拍板「v1 只支持逐个删除」的前提是 pack 技能可删——实证不成立：pack 技能落 org scope，`canManageScope` 对 org 恒 false（scope-membership.ts:180-191），权属链 `canManageSkill → managesArtifactHome`（scope-membership.ts:200-208）返回 false，**PUT 404 / DELETE 403**。因此 v1 卸载语义修正为：md 技能（personal scope）可删可改；**pack 技能不可逐个删除，卸载唯一路径 = 重传减项**（archiveRemoved 自动归档）。Skills 页按 `editable=false` 本就不对 pack 技能显示删除入口，UI 无需新增禁用逻辑。

### 第一节：总体链路

```text
选文件（accept=".md,.zip"，multiple，允许混选——拍板）
  → 前端魔数预检（PK\x03\x04，伪装 .zip 直接报错，不等解压炸掉）
  → 上传到 web-ui server（md=JSON 文件集；zip=流式）
  → server 集中完成：解压 → mini parser 解析 → isProbablyBinary 嗅探
    → GET /v1/skills 比对同名 → 返回预览清单
  → 用户确认（同名项逐条确认覆盖）
  → 执行注册（md → POST/PUT /v1/skills；zip → 受管目录 + register + import）
  → 结果明细（per-item 状态 + 原因）
```

通道分流：md 逐条进 `POST /v1/skills` 通道（落 personal scope）；zip 逐个进 local skill pack 通道（落 org scope）。**两通道技能分属两个 scope**：可见性一致（listVisibleSkills 合并），管理权不同（personal 可改可删，org pack 不可）——对可见性和将来卸载都有影响，已在概述修正条声明。

**server 侧单份规则副本**（插件不可 import core，这是唯一合法方式）：mini frontmatter parser（对齐 `src/skills/frontmatter.ts:30`）、name 校验（对齐 `src/skills/skill-name.ts:1`）、`isProbablyBinary`（复刻 `src/skills/seed.ts:14-17`：含 null 字节或 UTF-8 回环不等，**内容嗅探不按扩展名猜**）、normalize fallback（对齐 `normalizeSkill`：name 缺省回退目录名、description 缺省从 body 首段推导截 200 字符、body 空判 malformed）。同源管理于一个新文件内。

### 第二节：web-ui server 端点（DESKTOP-only）

新增 `plugins/web-ui/server/skill-upload.ts`（index.ts 已 2000+ 行，不继续加肥），index.ts 只挂两条路由。守卫照文件内惯例 `if (!DESKTOP) return json(res, 404, { error: "not found" })`（带空格）；admin 调用照 `coreFetch` + `PORTAL_IDENTITY_HEADER: desktopPortalToken` 先例（index.ts:1315-1319）。

**`POST /api/desktop/skills/upload/preview`**

- md：body 为 JSON `{files: [{name, text}]}`（readBody 1MB 上限够用，单 SKILL.md 远低于此）；
- zip：`application/zip` 流式落盘到 `<MEERKAT_DATA_DIR>/skillpack-uploads/.staging/<uploadId>/`（绕开 1MB JSON 上限，流式先例 stageUploadStream index.ts:648）；
- 返回预览项：`{name, description, source: "md"|"zip", zipName?, action, reason?, conflictId?, conflictSource?, conflictWarning?}`。action 枚举按通道分流：**md 项** = `create | overwrite | shadow | recreate | excluded`；**zip 项** = `create | update | skip-foreign | shaded | excluded`（语义见第三节两张表）。

**`POST /api/desktop/skills/upload/confirm`**

- md 项按 preview 的 action 执行：`create/recreate/shadow` → `POST /v1/skills`；`overwrite` → `PUT /v1/skills/:id`（conflictId）。**body 必须显式带 `principalId`**：surface 路由无 capability 时强制 `body.principalId`（createSkill surface.ts:915-918、updateSkill surface.ts:841-844，updateSkill 不像 getSkillDetail 那样回退 `actor.p`）；照 web-ui 现有先例（index.ts:1723 `POST /v1/skills` 带 `{principalId: user, ...draft}`、:1751 DELETE 带 `{principalId: user}`）；
- zip 项：staging 搬移到 `<MEERKAT_DATA_DIR>/skillpack-uploads/<slug>/`（已存在先清空）→ **查重** → register → import → 返回 ImportResult；
- **register 幂等（P0-1，必须照做）**：core store 层无 URL 判重（`packs.create` = randomUUID 直接 put，skill-pack-store.ts:55-58），应用层判重先例是种子流 `ensureSkillPacks`（index.ts:1036 `existing.find(...)`）。confirm 必须先 `GET /v1/admin/skill-packs` 按 url 精确匹配，已存在则**跳过 register 直接 import**。不判重会叠 pack：两个 pack 指向同一目录，`archiveRemoved` 按 packId 归档，互相把对方技能当减项归档，行为直接乱掉。
- import 调用**空 body 即可**：`selected` 缺省 `"all"`、`scopeIds` 缺省落 `pack.targetScopeId`（org scope）（skill-packs.ts:141-151）。
- register 参数固定：`{url: <受管目录绝对路径>, allowLocal: true, trustTier: "third-party", subset: "all"}`。

**受管目录与 slug**：slug = zip 文件名消毒（小写字母/数字/连字符），slug 即 pack URL 身份（重传同文件名 = 同一 pack）。staging 目录 `.staging/<uploadId>/` 在 confirm 时搬移，超时未 confirm 的 staging 定期清理。slug 规则本期定死，未来设置页加 pack 卸载入口不需要数据迁移。

### 第三节：预览与同名冲突语义（实证定稿）

**比对动作点名**：预览阶段由 **web-ui server 预览端点**调 `GET /v1/skills?principalId=...`（surface.ts:745-781，principalId 必填）一次拿全比对所需字段：`name / status（含 archived）/ scopeId / source / pack / editable / shadowed`。**页面不直接调 core**。注意返回的 archived 项只含当前用户 manageable 的（surface.ts:753-758）——即 archived pack 技能不出现，archived md 技能出现，与下方分支语义自洽。

同名冲突语义**按通道切分**——md 项的 confirm 走 POST/PUT，zip 项的 confirm 走 pack import，两通道的同名行为机制完全不同，预览标注必须分别如实。

**md 通道同名三分支**（全部代码实证）：

| # | 已有同名技能 | 实证依据 | confirm 动作 | 预览标注 |
|---|---|---|---|---|
| 1 | personal 自己的 md 技能（active，editable=true） | `canManageScope` personal samePerson → PUT 通 | `PUT /v1/skills/:id` 覆盖 | 「⚠ 已存在，将覆盖」 |
| 2 | personal 已归档（archived，editable=true） | `createOwnedSkill` 对 archived 同名**不 409**，硬删旧记录重建（app-skills.ts:418-420）；`updateOwnedSkill` 对 archived 返回 null（app-skills.ts:263） | `POST /v1/skills` 新建 | 「将重新创建（原同名技能已删除）」 |
| 3 | org pack 技能（出厂包或上传包，editable=false） | org 恒不可管理 → PUT 404；不同 scope 不触发 409；`visibleFor` 顺序 personal 优先（app-skills.ts:240） | `POST /v1/skills` 创建 personal 同名技能形成 **shadow** | 「⚠ 将创建你的同名版本覆盖显示；原版本随包管理不受影响，删除你的版本后恢复」；出厂包追加「该技能随安装包分发，升级可能回灌」 |

分支 3 的 shadow 语义：`/<name>` 调用命中 personal 版（resolution 顺序 personal 在 org 前）；pack 重 import 不碰 personal 版（`foreignSkillCollision` 只查同 scope）；删除 personal 版后 pack 版恢复可见——**可逆的覆盖**，是 PUT 不可行下的正解。

**zip 通道同名三态**（import 机制实证，`foreignSkillCollision` seed.ts:75-84：同 scopeId + 同名 + 异 createdBy + 非 archived → upsert 返回 `"foreign"`，`importPack` 归入 skipped，ingest.ts:273-275）：

| # | 已有同名 | import 实际行为 | 预览标注（action） |
|---|---|---|---|
| 1 | org **同 pack** 技能（重传同 slug） | createdBy 相同 → upsert 更新 ✓ | 「将更新」（`update`）——唯一与直觉一致的情形 |
| 2 | org **异 pack** 技能 active（出厂包 / 其他上传包同名） | foreign 命中 → **静默跳过**，资产也装不上；发生在 upsert 阶段，`planIngest` 五种排除原因码覆盖不到 | 「⚠ 与 \<pack 标签\> 中同名技能冲突，导入时将被跳过」（`skip-foreign`；SkillPack 无 name 字段，标签由 `GET /v1/admin/skill-packs` 映射 packId → url 后派生：上传包取 slug、git 包取仓库名） |
| 3 | personal active（自己的 md 技能同名） | foreign 只查 org scope，personal 不挡 → pack 版正常安装，但 `visibleFor` personal 优先 → **被旧 personal 版遮挡**，`/<name>` 仍调用旧版 | 「⚠ 你的 personal 同名版本将遮挡导入结果（`/<name>` 仍调用你的版本）；如需使用导入版本，请先删除你的 personal 同名技能」（`shaded`，仍执行导入） |

分支 2 是真实高频场景（用户把出厂包技能改一改打包传上来），预览必须能报——server 比对时拿 existing skill 的 `pack.packId` 与本次 slug 对应 pack（按受管目录 URL 查到的）比对：同 id → `update`，异 id → `skip-foreign`，无 pack（首传）→ org 同名一律 `skip-foreign`。

分支 3 拍板（默认）：confirm **不自动归档** personal 版——隐式归档用户自建技能有破坏面，保持现状 + 文案如实 + 给出路；用户要切换自己删 personal 版（可逆）。

**排除项**（两通道通用）：原因码一次做全 `malformed / private / scope / collision / binary-asset`（对齐 `planIngest`，ingest.ts:173-211），预览标红并给出路文案，例：「含二进制资产 xxx.png，将被排除，请移除后重传」。binary-asset 是最大坑（core ingest 会把含二进制资产的 skill 整个排除），必须前置检出，不允许注册后静默缺席。zip 通道的 `collision` 判定用 `nativeNamesFor`（内建名），与 foreign（异 pack 用户内容撞名）是两回事，预览文案不得混淆。

### 第四节：zip pack 通道语义（实证定稿）

- **重传 = 覆盖受管目录 + 重 import**：增/改项 upsert（installed/updated），**减项自动归档**（`archiveRemoved`，app-skills.ts:61-72，每次 import 都执行）——「只增不改不减」的调研推断有误，更正为「重传以 zip 内容为准」。
- **复活语义**：`upsertSeedSkillUnsafe` 的 existing 查找不过滤 status（seed.ts:101-111），已归档的 pack 技能被重传带回会 review+publish 复活——这是「重传以 zip 内容为准」的一体两面，属预期。
- **无自动变更**：周期同步不启动（`SKILL_SYNC_POLL_MS` 缺省 0，config.ts:458；wiring.ts:1495 仅 `>0` 才启动）；register 固定 `syncMode: "pinned"`（skill-packs.ts:103），pinned 只更新 `updateAvailable` 标志不 reconcile；`maybeStartSkillPacks` 只管 seeds 出厂包。core 重启后上传包状态不变。
- **pack 技能权属**：org scope 恒不可管理（见概述修正条），PUT 404 / DELETE 403；md 技能落 personal scope，PUT/DELETE 均通。

### 第五节：安全与上限

- zip 魔数 `PK\x03\x04`：前端预检 + server 复验，伪装 .zip 直接报错；
- 上限对齐 readTree（pack-fetcher.ts:196-197）：zip 本体 ≤32MB，解压后总量 ≤32MB、文件数 ≤5000；
- zip slip 防护：解压路径规范化 + 受管目录前缀校验，拒绝 `..` 穿越与绝对路径条目；
- slug 消毒（仅小写字母/数字/连字符，碰撞时追加短哈希）；
- staging 超时清理；受管目录写入前清空旧内容（重传语义）；
- `trustTier` 固定 `"third-party"`（用户本地内容，不提升信任级）。

### 第六节：UI 落点

- **Skills 页页头**：`plugins/web-ui/src/skills.ts:534` 的 `listPageTpl` 目前单 action（`New skill`），扩展为 action 组：「本地上传」（主）+「New skill」；
- **上传弹窗**（新文件 `plugins/web-ui/src/skill-upload-dialog.ts`）三步：
  1. 选文件（`accept=".md,.zip"` multiple，可拖拽）；
  2. 预览清单：合并展示、按来源分组（md 组 / 各 zip 组）；每项显示 name + description + 状态徽标，全六态：新建 / ⚠覆盖 / ⚠shadow / 重新创建 / 标红排除（md 五态）+ 将更新 / ⚠冲突将跳过 / ⚠被遮挡（zip 三态，排除共用标红）；确认按钮在存在覆盖/shadow 项时要求逐条勾选或一键「全部确认」；
  3. 结果明细：per-item `created / updated / recreated / shadowed / skipped / excluded / failed` + 原因，失败项可重试。`skipped` 必装两种情形：zip 重传内容未变（`sameManifest` 相同 → upsert 归 skipped，seed.ts:107）与 `skip-foreign` 项（实际落在 ImportResult.skipped 里）——文案区分「内容未变，跳过」与「同名冲突，跳过」；
- i18n：全部文案走 `i18n()`，词条进 `plugins/web-ui/src/locale/zh-cn.ts`（加词条前 grep 防重复 key，no-dupe-keys 教训）。

> 拍板记录（Brainstorming 2026-08-26，四题）：① 开关语义 = core 默认关、桌面端 proc.rs env 开启（上游语义零变化）；② 呈现方式 = 兜底产物挂聊天附件卡片、视同交付——噪声过滤升级为承重设计，卡片 >5 合并汇总/截断 + operator log，与显式交付的去重是硬依赖；③ 后台任务写入本期不兜底，FILE_SEND_GUIDANCE 写明交付边界；④ 变更检测 = mtime 单次扫描——turnStart 毫秒精度、噪声在 find 表达式 prune、cp -p/unzip 保 mtime 漏检登记为可接受缺陷
> 设计评审（2026-08-26 一轮 3 条）：§5 outbox 原件不在去重覆盖内（阻断级——cp 进 outbox 是指引标准动作，原件留 workspace 必触发双卡片，修法 = 路径 + 内容哈希双集合）；§1 seed 碰撞（`:sweep` 后缀照 `:scratch` 先例）与 collect 落点（attachments.ts 新增导出 `collectWorkspaceSweep`）；§4 汇总文本载体落实（delivery session entry text 尾注，不碰回复文案路径）

### 概述

交付仅两条通道（DM 的 `$AGENT_OUTBOX` 与 `post(files)`），都依赖模型自觉；本地模型不遵循指引时，会话产出只留在沙箱 workspace，「文件」面板（artifact 注册表）不可见、无下载入口，模型还会幻觉「复制到 workspace 即可见」误导用户。本设计在 DM turn 收口处追加**兜底扫描**：检测本轮 workspace 新建/修改但未交付的文件，自动登记为 artifact（归属当前用户）并挂聊天附件卡片，使会话产出必然可见。涉及 core turn 收口与 artifact 注册，记 ADR-012。

### 第一节：总体结构

DM turn 收口块（`orchestrator.ts:2744-2774`）在 outbox 收集（`:2748-2761`）之后、`outbound` 合流（`:2769`）处追加 fallback sweep：

- 触发条件：`harvestOutbox`（`conversation.kind === "dm"`，`:2747`）、非 automated turn（`automatedTurn = input.origin.kind === "automation"`，`:402`）且开关开启；
- 扫描范围：`box.handle` 与 `scratchBox.handle` 两个 workspace（与 outbox 覆盖范围一致）；**扫描根 = 各 handle 的 workspace 根**——`sandbox.run` 的 cwd 即 `handle.rootDir` = workspaceDir（`wsl2-sandbox.ts:308`、`:349`），find 以 `.` 为根、输出 workspace 相对路径，与 `readFileBytes(handle, rel)` 语义一致，不是 $HOME；
- 命中文件合并进 `outbound.attachments` → 聊天附件卡片（`finalResult.attachments`，`:3079`/`:3094`）与「文件」面板（artifact 注册表 → `/api/files`）经现有路径自然呈现，**零新增渲染/展示代码**。

**seed 隔离**：artifact id = `fileArtifactId(seed, "out", batchIndex)`，三条通道（outbox / post / sweep）的 batchIndex 各自从 0 计——scoped box 的 sweep 注册用 `{ ...fileRegistration, seed: \`${fileRegistration.seed}:sweep\` }`，scratch box 的 sweep 再叠一层用 `:sweep:scratch`（两次 sweep 调用 batchIndex 各自从 0，共享 seed 会撞 artifact id；照 scratch 的 `:scratch` 先例（`orchestrator.ts:2765`）再加后缀隔离），turn 内不撞 id；跨 turn 因 seed 含 runId 天然不冲突。

**collect 落点**：`registerArtifact`/`uniqueName` 是 attachments.ts 模块私有（`:158` 等），orchestrator 侧无法自行组装注册——attachments.ts 新增导出 `collectWorkspaceSweep`（与 `collectOutbound`/`collectNamedOutbound` 同层），内部复用私有助手；orchestrator 只负责调用与合并。签名骨架：

```ts
collectWorkspaceSweep(sandbox, handle, opts: {
  turnStart: string;                // 毫秒精度时间戳
  tracker: DeliveredTracker;        // 本 turn 已交付路径 + 哈希
  cardBudget: number;               // 本 handle 可用卡片额度
  register?: ArtifactRegistration;  // seed 已带 :sweep
}): Promise<{
  attachments: OutgoingAttachment[];   // ≤ cardBudget，挂卡
  registeredOverflow: string[];        // 已注册未挂卡
  duplicates: string[];                // 去重跳过
  dropped: number;                     // 超登记上限
}>
```

### 第二节：开关与配置

- core config 新增 `deliverWorkspaceOutputs: boolEnvStrict("DELIVER_WORKSPACE_OUTPUTS", ...) ?? false`（照 `config.ts:905` `allowLocalSkillPacks` 先例），**默认 false**——上游语义零变化；
- wiring 将开关注入 orchestrator deps（确切接线行执行计划定）；
- 桌面层 `proc.rs` 照 `.env("ALLOW_LOCAL_SKILL_PACKS", "1")` 先例（`:261`）注入 `DELIVER_WORKSPACE_OUTPUTS=1`。

### 第三节：变更检测（mtime 单次扫描）

turn 结束一次 `sandbox.run(handle, findCmd)` 执行 `find`，**噪声在表达式里 prune**（不做事后内存过滤——npm install 后的几千行输出全进 core 内存再筛不可接受，prune 在遍历侧直接剪掉，输出量就是真实产出量级）：

```sh
find . \( -path './.agent-turn' -o -path '*/node_modules' -o -path '*/.git' \
       -o -path '*/__pycache__' -o -path './.npm' -o -path './.cache' \
       -o -path './venv' -o -path './.venv' \) -prune \
     -o -type f -newermt '<turnStart 毫秒精度>' -print
```

- **时间戳精度**：`-newermt` 是严格大于，turnStart 必须带毫秒小数（如 `@1692960000.123` 或 ISO 带小数），不能截到秒——否则 turn 头 1 秒内的产出（最常见：模型一上来就写文件）恰好落在边界上被漏检；
- **已知限制（登记为可接受缺陷）**：`cp -p`/unzip 保 mtime 的文件漏检；真有用户踩到，后续升级为快照 diff 是纯增量，不推翻本期结构。

### 第四节：噪声清单与上限（承重设计）

兜底产物挂聊天卡片，噪声直接占用用户注意力——噪声过滤在本设计是**承重**的，不是体面问题。

- prune 常量清单：`.agent-turn`（turn 私有 inbox/outbox，`attachments.ts:23`）、`node_modules`、`.git`、`__pycache__`、`.npm`、`.cache`、`venv`/`.venv`——清单集中一处常量，执行期可补；
- 登记上限：单 turn ≤20 个（复用 `MAX_OUTBOUND_FILES`）、单文件 ≤`MAX_ATTACHMENT_BYTES`（1GB）；超出计入 dropped + operator log；
- **卡片额度**：`SWEEP_MAX_CARDS = 5`，两 handle 共享；超出的文件**仍注册**（Files 面板可见）但不挂卡片。显式交付（outbox/post）不设此限——那是用户明确意图，噪声约束只针对兜底；
- **汇总文本载体**：delivery session entry（`orchestrator.ts:2810-2826`）的 `payload.text = deliveryManifest(...)` 是 core 侧既有文本——sweep 挂卡部分并入 `outbound.attachments` 后 text/files 自动覆盖；溢出部分在 text 末尾追加 `"; and N more file(s) registered to the Files panel: name1, name2, …"`（英文，与现有 manifest 风格一致；实现上给 `deliveryManifest` 加可选尾注参数或调用处拼接，执行计划定）。不新增 entry 类型、不动回复正文。边界自洽：溢出存在的前提 = 5 张卡已满 → `outbound.attachments` 非空 → delivery entry 必然存在，尾注不会无处安放；
- hidden tape note（`:2835`）与 `recentDeliveryNote`（`attachments.ts:344`）同步生效——模型下轮知道哪些文件被自动登记；
- **operator log**：溢出/超上限/去重明细走 `console.error`，照 orphans 警告先例（`orchestrator.ts:2765`）。

### 第五节：去重（路径 + 内容哈希双集合，硬依赖）

去重错了 = 同一附件卡片在聊天里出现两次，用户立刻可见。**评审实证的路径集合盲区**：agent 按指引 `cp report.pptx $AGENT_OUTBOX/` 后原件留在 workspace、mtime 是新的——outbox 交付的是副本路径，原件路径 core 侧不可知，纯路径集合盖不住，兜底会再挂一张卡。这不是边角案例：cp 进 outbox 正是 FILE_SEND_GUIDANCE 教的标准动作，守规矩的 agent 每次交付都会触发。修法定稿：

- per-turn `DeliveredTracker = { paths: Set<string>, hashes: Set<string> }`，orchestrator 在 turn 开始时创建；
- `collectOutbound` 本就逐文件读字节（`attachments.ts:374`）——返回结构追加 `hashes: string[]`（sha256 hex），orchestrator 并入 tracker；
- `collectNamedOutbound`（post(files) 通道）同理（`:420` 已读字节）——返回 `hashes`；`resolveFiles`（`surface-tools.ts:198`）成功交付时把规范化相对路径记入 tracker.paths（`createSurfaceToolDeps` 传入 tracker）；
- sweep 命中候选后反正要 `readFileBytes` 才能注册——**注册前算 sha256，命中 hashes 即跳过**；路径命中 paths 亦跳过；
- 成本每文件一次 sha256，可忽略；同内容不同路径的第二份一并跳过，视为正确语义（同内容已交付）。

### 第六节：指引文本配套

`FILE_SEND_GUIDANCE`（`pi-tools.ts:627`）补后台任务交付边界一句：「后台任务写的文件请在任务完成后的对话里交付」——让模型有指引可依，而不是靠用户踩坑发现。

### 第七节：边界与限制

- 仅 DM 会话（`harvestOutbox` 门控）；群聊等其余 kind 行为不变；
- automated turn（cron/wake 触发）不兜底：与「后台任务写入本期不管」同一条边界；同时保住 poll 静默分支（`orchestrator.ts:3084` 的 `isPollFire && !outbound.attachments.length && isSilentPollReply(reply)`）不被 sweep 附件破坏——本想静默的轮询 turn 若挂上附件会转成 `status:"ok"` 把回复发出去，cron 频繁打扰用户；
- 仅 workspace 内：`/tmp` 等非 workspace 写入不兜底；
- 后台任务 turn 外写入本期不兜底，且 mtime 检测在原理上就扫不到它——turn 结束后写成的文件，到下一 turn 开始时 mtime 已陈旧（mtime < 新 turn 的 turnStart），任何后续 turn 的兜底都不会扫到它；`FILE_SEND_GUIDANCE` 的边界句（第六节）是这条边界的唯一防线，不是配套优化；
- 同一文件跨 turn 再改再登——每 turn 独立 artifact（seed 含 runId），Files 面板呈现新版本条目，不冲突；
- `cp -p`/unzip 保 mtime 漏检（第三节，可接受缺陷）。

### 第八节：测试（turn 级集成，TDD 先行）

1. DM turn 产出未交付文件 → 注册表出现 artifact（owner = 当前用户 personal scope）、回复带附件卡片、delivery entry text 覆盖；
2. `post(files)` 已交付的文件 → 不重复登记、聊天仅一张卡片（paths 命中）；
3. **cp 进 outbox 后原件不重复挂卡**（hashes 命中——评审阻断修复的回归用例）；
4. `node_modules` / `.agent-turn` 等噪声 → 不登记；
5. 开关关闭 → 不兜底（上游语义保持）；
6. >5 个产出 → 卡片 5 张 + delivery entry 尾注汇总 + 其余仍注册（Files 面板可见）+ operator log；
7. seed 隔离：同 turn outbox / post / sweep 三通道并存 → artifact id 不冲突；
8. automated DM turn（cron 触发）产出文件 → 不兜底，poll 静默分支行为不变。

### 第九节：ADR 摘要（ADR-012）

DM turn 收口新增兜底登记通道（automated turn 除外，保住 poll 静默分支）。动机：桌面「单用户 + 本地弱模型 + 用户预期文件可见」下，上游「显式交付 = 意图过滤」的假设反转。缝改动清单：`orchestrator.ts`（收口块接线 + tracker）、`attachments.ts`（`collectWorkspaceSweep` 新导出 + `collectOutbound`/`collectNamedOutbound` 返回 hashes）、`surface-tools.ts`（`resolveFiles` 记录 tracker）、`config.ts`（开关）、`wiring.ts`（开关注入 orchestrator deps）、`pi-tools.ts`（FILE_SEND_GUIDANCE 一句）。默认关保住上游语义，桌面经 proc.rs env 开启。（完整背景/被否决方案/后果见 [ADR.md](./ADR.md)。）

### 第十节：不做

- 后台任务/cron turn 外写入与 automated turn 的兜底（指引边界已写明；后续若做，走任务完成时的登记钩子——届时 poll 静默分支的取舍需一并重审）；
- workspace 外写入的兜底（`/tmp` 等）；
- 快照 diff 变更检测（`cp -p` 漏检的升级路径，纯增量，需要时再做）；
- 群聊会话兜底（DM 先行；群聊的 owner 归属与噪声放大问题另行评估）；
- 桌面以外形态开启（开关默认关，其他部署形态自行评估）。

# 基于 qm 二次开发的 Meerkat 企业级 Agent

本目录归档 Meerkat（基于 qm 私有 fork 的二次开发）的**全部需求与设计文档**，目标是每个二开需求都可追溯：**需求 → 调研 → 设计 → 决策 → 计划 → 实现**，任何一环都能指回上一环。

## 目录结构

```text
docs/meerkat/
  README.md              ← 本文件：目录说明与归档约定
  v0.0/                  ← 一个二开需求 = 一个版本目录
    需求描述.md           ← 业务方原始需求（产品定位、客户、功能、约束）
    需求调研.md           ← 针对需求的代码库调研结论（可行性、机制、边界）
    设计文档.md     ← 定稿设计文档（评审通过，开发依据）
    ADR.md               ← 架构决策记录（关键取舍 + 被否决方案及原因）
    执行计划.md           ← 任务级实施计划（Task 拆解 + checkbox 追踪，执行依据）
    本地部署.md           ← 可选：运维向部署/运行文档（环境、步骤、踩坑、限制）
  v0.1/                  ← 下一个需求，同样五件套 + 交付三件套（+ 可选部署文档）
    ...                  ← 五件套同上
    发布文档.md           ← 交付型需求必备：如何从源码构建出交付物（release 链路）
    用户文档.md           ← 交付型需求必备：终端用户使用说明
    CHANGELOG.md         ← 相对上一版本的变更记录（Added/Changed/Fixed/Known Issues）
  ...
```

## 归档约定

1. **一个需求，一个版本目录**。按 `v0.0`、`v0.1`、`v0.2` 递增（低位跟随 qm 上游版本号，不用 1.x）；目录一旦随对应开发完成而冻结，不再修改。需求变更或返工走新版本目录，不回改旧目录。
2. **五件套齐全才算归档完成**（交付型需求另加交付三件套）：
   - `需求描述.md` —— 业务语言写就，回答「做什么、为谁做、为什么」；
   - `需求调研.md` —— 对着代码库写，回答「现状是什么、哪些能复用、边界在哪」，每个结论须指明文件与位置；
   - `设计文档.md` —— 设计定稿，回答「怎么实现」，须经评审通过（评审中发现的必修项全部闭环）后方可作为开发依据；
   - `ADR.md` —— 只记「关键取舍」，每条含背景、决策、被否决方案及原因、后果；
   - `执行计划.md` —— 把设计文档拆成可执行的 Task 序列，回答「按什么顺序、用什么步骤实现」，每个 Task 含文件清单、接口契约、测试与提交步骤，checkbox 逐项追踪进度；须经评审通过后方可动工，执行中的完成状态实时回写本文件。
   
   交付三件套（产出物要交到客户手里的版本必备）：
   - `发布文档.md` —— 面向开发者：从源码到安装包的完整 release 链路（前置条件、步骤、产物、CI、踩坑），换人也能照样出包；
   - `用户文档.md` —— 面向终端用户：安装、首启配置、日常使用、数据位置、常见问题，不写实现细节；
   - `CHANGELOG.md` —— 相对上一版本的全部变更（Added/Changed/Fixed/Known Issues），core 内核缝改动单独标注并指回 ADR。
3. **与 qm 内核文档的边界**。`docs/meerkat/` 之外的 `docs/` 属于 qm core，保持与上游字节一致；Meerkat 的所有文档只写在本目录下，保证 `update-qm` 合并上游时零冲突。
4. **分支约定**：`main` 只用于跟随上游主仓升级，保持与 upstream 可快进合并的状态，**二开成果一律不合并回 `main`**；所有二开开发在功能分支（如 `feature/meerkat`）上进行，上游同步由 `update-qm` 向功能分支合并 upstream/main。
5. **设计文档与实现的一致性**。实现过程中对设计的偏离，必须回写 `设计文档.md`（冻结前）或在 `ADR.md` 补一条新决策（冻结后），不允许代码与文档长期分岔；执行计划与实际顺序的偏离同理，回写 `执行计划.md`。
6. **部署文档按需补充**。版本涉及环境搭建或调试排障时，补一份 `本地部署.md`：只写可复现的步骤和已验证的坑，不写设计内容（设计归设计文档）。

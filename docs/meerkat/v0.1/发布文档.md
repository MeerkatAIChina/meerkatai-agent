# 发布文档

> 如何在一台开发机上从源码构建出 Meerkat 桌面版安装包（release）。本文档的每一步都在 Windows 10 上实测通过；macOS 走同一条链路（CI 已建 matrix，真机未验证）。

## 前置条件

| 工具 | 版本 | 说明 |
|---|---|---|
| Node.js | ≥ 24（staging 用 v24.15.0） | 建议装在默认路径 `C:\Program Files\nodejs` |
| Rust 工具链 | stable（rustup 安装） | `~/.cargo/bin` 需在 PATH |
| Visual Studio 2022 Build Tools | "使用 C++ 的桌面开发"工作负载 | Windows 链接器（link.exe）来源，**不装 C++ 负载会报 linker 缺失** |
| Git Bash | 任意 | staging 脚本是 bash |
| npm 依赖 | root 与 `plugins/web-ui` 各 `npm ci` 一次 | 第一次构建前装好 |

macOS 额外需要：Xcode Command Line Tools。不需要 Docker（沙箱不在包内）。

## 一次性准备：更新签名密钥

自动更新包需要签名校验。首次生成：

```bash
cargo install tauri-cli --version "^2"   # 或 npm i -g @tauri-apps/cli@2
tauri signer generate -w ~/.tauri/meerkat-desktop.key
```

- 密码可留空（CI/本地构建都以空密码使用）
- **这个私钥一旦更换，老客户端将无法校验新包**，务必备份；公钥已写死在 `src-tauri/tauri.conf.json` 的 updater pubkey 字段，换 key 要同步改它

## 本地构建三步

在仓库根目录执行：

### 1. 组装载荷（payload）

```bash
export PATH="$PATH:/c/Program Files/nodejs"
bash deploy/layers/meerkat/desktop/scripts/stage-payload.sh
```

这一步会：拷 Node 运行时 → esbuild 把 core 和 web-ui server 打成单文件 → 构建 web-ui 前端 → classifier 装生产依赖 → 拷种子配置。产物在 `deploy/layers/meerkat/desktop/payload/`（约 148MB）。

脚本幂等，每次先清空旧 payload 重建。改了 `src/`、`plugins/web-ui/`、classifier 或种子后必须重跑。

### 2. 冒烟验证（可选但建议）

```bash
bash deploy/layers/meerkat/desktop/scripts/verify-payload.sh
```

从 payload 直接起 core，跑一轮对话 + 一轮分类路由，确认裁剪没有伤到运行时。

### 3. Tauri 打包

```bash
cd deploy/layers/meerkat/desktop
export PATH="$HOME/.cargo/bin:$PATH"
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/meerkat-desktop.key | tr -d '\r\n')"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""
MSYS2_ARG_CONV_EXCL="*" tauri build
```

产物：

```text
src-tauri/target/release/bundle/nsis/Meerkat_0.1.0_x64-setup.exe      ← 安装包
src-tauri/target/release/bundle/nsis/Meerkat_0.1.0_x64-setup.exe.sig  ← 更新签名
```

`build.rs` 会检查 payload 是否存在——没跑第 1 步直接 `tauri build` 会在 release 模式下直接报错。

## CI 发布（推荐正式渠道）

`.github/workflows/desktop-release.yml`：推一个 `desktop-v*` 标签即触发三平台 matrix（windows x64 / macOS arm64 / macOS x64）：

```bash
git tag desktop-v0.1.1 && git push origin desktop-v0.1.1
```

CI 自动完成：staging → 冒烟 → tauri-action 构建签名 → 上传 GitHub Release。需要仓库 secrets 里配好 `TAURI_SIGNING_PRIVATE_KEY` 和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。

**注意**：CI 产物上传的是私有 GitHub Release，客户拿不到；对外分发要再把安装包转存到客户可达的渠道（OSS/交付函）。自动更新的 `latest.json` 托管地址目前还是占位符（见设计文档第七节遗留项）。

## 踩坑记录

1. **`tauri build` 超时被杀**：cargo 全量编译 Rust 依赖要几分钟。构建是**增量**的，超时后原样重跑同一命令即可续编，不会从头再来。
2. **报 linker / `link.exe` 缺失**：VS Build Tools 没装 C++ 工作负载。装完后如果还报，先跑 `scripts/cargo-msvc.bat` 再构建。
3. **payload 旧了**：表现是"装了新包但行为没变"。`stage-payload.sh` 必须在每次代码改动后重跑，tauri build 不会自动重建 payload。
4. **签名 key 路径含 `\r`**：Windows 下私钥文件可能带 CRLF，`cat | tr -d '\r\n'` 这步不能省，否则签名校验静默失败。
5. **版本号**：安装包版本号来自 `src-tauri/tauri.conf.json` 的 `version` 字段，发新版前先改它，否则覆盖安装判定会混乱。

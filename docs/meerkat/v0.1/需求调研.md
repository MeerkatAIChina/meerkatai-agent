# 需求调研文档

## 需求一：桌面化的交付物

> 调研日期：2026-08-12 · 结论：**可行，难度中等** · 推荐路线：Tauri v2 + 随包 Node 运行时 + sidecar 三进程

### 1. 现状盘点：要打包的是什么

当前系统不是"一个网站"，而是**三个 localhost 进程 + 一段引导注册序列**（`scripts/meerkat-local-up.sh` 完整描述了启动拓扑）：

| 组件 | 启动方式 | 说明 |
|------|---------|------|
| 分类 sidecar :8090 | `tsx src/server.ts`（`deploy/layers/meerkat/classifier/`，node_modules 47MB） | 敏感度分类，PII/TRIZ/语义三层 |
| qm core :8081 | `node --env-file-if-exists=.env src/index.ts`（`package.json:13`，要求 Node ≥24.15，TS 直跑） | 核心 API + orchestrator |
| web-ui :8096 | `node server/index.ts`（`plugins/web-ui/`，node_modules 366MB） | Vite 构建的 `dist-web/` 静态资源 + 到 core 的签名代理（`plugins/web-ui/server/index.ts:1-33`） |
| 引导注册 | bash + curl 调 admin API（`meerkat-local-up.sh:54-104`） | 注册 providers、导入 skill packs、设 org 默认模型——core 启动后必须执行，否则界面没有模型 |

运行时还有三类**文件系统依赖**，决定了"打成单文件 exe"不现实：

- **协议 md 文件运行时读盘**：`loadProtocolFile()`（`src/resolution/prompt-vars.ts:6`）在 core 启动时从源码目录读 `shared-core.md` 等提示词文件（`src/core/orchestrator.ts:177-180`）
- **Skills 物化写盘**：skill packs 物化到 `skills/` 目录（`src/skills/materialize.ts`、`src/skills/materialization-paths.ts:1`）
- **数据目录**：`DATA_DIR` 默认 `./data`（`src/config.ts:583`）；配置面 = `.env` + `deploy/layers/meerkat/models.conf` + `providers/*.conf` + `skillpacks.conf`

重量级事实：

- 依赖体积：root `node_modules` **1.5GB**（含 dev 依赖）、web-ui 366MB、classifier 47MB——全量打包不可接受，必须裁剪
- `pi-coding-agent` 内含 darwin/win32 原生 `.node` 预编译（TUI 用，headless core 用不到，但打包脚本必须显式排除或按平台取舍）
- **Docker 沙箱是可选的**：daemon 不可达时聊天照常、沙箱工具（execute/write/read）不可用（`meerkat-local-up.sh:37-39`；orchestrator 测试证实对话 turn 不 provision 沙箱）
- **无 Postgres 时全部走内存存储**（`src/wiring.ts` 的 `artifactMap` 双后端）：重启丢会话（部署文档 FAQ Q10 已如实记录）
- 本地模式 core 无认证绑 localhost；chassis 层已有 `CORE_SIGNING_SECRET` 签名机制（`plugins/web-ui/server/index.ts:14-19` 引用），桌面版应启用

### 2. 技术路线对比：Node 载荷怎么进 Tauri

| 方案 | 做法 | 优点 | 风险/代价 |
|------|------|------|----------|
| **A. 随包 Node 运行时**（推荐首版） | node-v24 官方二进制 + 源码 + 生产裁剪 node_modules 作为 Tauri resources，三个进程共享一个 node | **零代码改造**；Node 24 默认开启 TS type-stripping，源码直跑；协议 md、skills 物化等文件行为原样成立 | 体积最大（裁剪后估 300-400MB）；源码可读 |
| B. esbuild + Node SEA | 每个进程 esbuild 打成 CJS 单文件 → Node SEA 注成单 exe | 体积小、源码不可读 | 要处理 `.node` 原生文件排除、协议 md 外挂 assets、动态 require 兼容性；pkg 已废弃，SEA 的 ESM 支持历史坎坷（nodejs/node#53565）；调试链长 |
| C. Bun/Deno compile | 换运行时一把编译 | 单文件最干净 | qm 依赖 Node 特有行为（`require(esm)`、strip-types、node:test），兼容性需逐个验证，首版不赌 |

外部依据：

- **Tauri v2 官方文档有「Node.js as a sidecar」专题指南**（tauri-docs v2, sidecar-nodejs.mdx）：`bundle.externalBin` 打包外部二进制 + shell 插件拉起子进程，是官方背书的标准做法，并明确记载"也可以直接嵌入 Node 运行时 + JS 资源"（即方案 A）
- **同构先例**（2026-08，Stream Facility devlog）：Tauri v2 壳 spawn Node sidecar → 轮询 TCP 就绪 → WebView 指向 localhost → 关窗回收子进程，与本项目拓扑完全一致，验证了方案 A 的工程闭环
- 桌面 OS 限制：sidecar 模式仅适用桌面（Windows/macOS/Linux），官方指南明示 "applicable for desktop operating systems only"

### 3. 推荐架构

按 fork 规则，Tauri 工程属组织专属，放 `deploy/layers/meerkat/desktop/`：

```text
deploy/layers/meerkat/desktop/
  src-tauri/          ← Rust 壳：进程管理 + 窗口 + 自动更新
  payload/            ← 打包 staging（构建时生成）
    node/             ← node-v24 运行时（按平台）
    core/             ← src/ + 裁剪 node_modules + 协议 md
    classifier/       ← 分类 sidecar + 裁剪 node_modules
    web-ui/           ← dist-web/ + server/ + chassis/ + 裁剪 node_modules
    config/           ← models.conf / providers / skillpacks.conf（安装后可编辑）
```

- **进程管理（Rust）**：选空闲端口（或固定 127.0.0.1 三端口）→ 拉起 classifier → core → 健康轮询 → 执行首启引导（注册 providers/skill packs/默认模型，把 `meerkat-local-up.sh:54-104` 的 curl 序列移植成 Rust reqwest 或 node 引导脚本）→ 拉起 web-ui → 打开 WebView 指向 `http://127.0.0.1:<web-ui 端口>` → 关窗时回收全部子进程
- **配置与数据落点**：`DATA_DIR` 指向 OS 应用数据目录（Tauri path API 注入 env）；providers 的 API key 做成首次启动的设置页或明文配置文件（沿用 .env 机制）
- **安全**：启用 `CORE_SIGNING_SECRET`，webview ↔ web-ui ↔ core 全链签名；core 只绑 127.0.0.1
- **分发**：Windows NSIS 安装包（需代码签名证书，否则 SmartScreen 拦截）；macOS .app/.dmg（需 Apple Developer ID + notarization 公证）；`tauri-plugin-updater` 自动更新
- **CI**：GitHub Actions matrix（windows-latest x64、macos-latest arm64/x64 universal），tag 触发发版

### 4. 关键边界与风险（按严重度排序）

1. **沙箱缺位（高）**：客户机没有 Docker → execute/write/read 工具不可用 → "资料查找、生成报告"场景受损。选项：a) 桌面首版不带沙箱、产品限制明示（对话与路由能力完整）；b) 等需求二（自研沙箱）落地后以资源形式打进安装包；c) 工具裸跑（否决，违背安全设计）。**建议 a → b**，不阻塞 Tauri 主线
2. **会话不持久（中）**：无 Postgres → 内存存储，重启丢会话。桌面单机场景的合理演进是 SQLite 后端（Node 24 原生 `node:sqlite`），属新工作项；首版可接受丢会话，但要在产品说明中明示
3. **载荷体积（中）**：全量 1.9GB 不可接受。裁剪路径：`npm --omit=dev` 生产安装 + 排除桌面用不到的 connector 依赖（Slack/AWS SDK 等大头）+ 排除 pi-tui 原生预编译。目标安装包 <400MB，**需实测迭代**，是工作量最大变数
4. **本地无认证（低-中）**：本地模式 core 无认证，本机任意进程可调 8081。桌面交付必须启用 `CORE_SIGNING_SECRET`（机制现成，只是配置问题）
5. **移动端（信息项）**："后期支持 Android/iOS"——iOS 不允许这种子进程/本地服务形态，意味着移动端是**远程后端 + 轻客户端**的另一套架构，不是本方案的延伸。立项移动端时单独评估，不影响桌面版决策
6. **签名与公证（低）**：纯流程成本，证书需采购（Windows 代码签名证书、Apple Developer 账号 $99/年），公证每次发版增加几分钟 CI 时间

### 5. 工作量估算（人日，粗估）

| 工作项 | 估时 |
|--------|------|
| Tauri 骨架：Rust 进程管理 + WebView + 生命周期 | 3-5 |
| 载荷裁剪与 per-OS 打包脚本（含体积实测迭代） | 5-8 |
| 首启引导移植（注册序列）+ 配置面落地 | 2-3 |
| 签名/公证/CI 矩阵（不含证书采购周期） | 3-5 |
| 端到端联调验收（模型路由/会话锁/Skills 在桌面环境复验） | 3-5 |
| **合计** | **16-26 人日** |

主要不确定性在载荷裁剪（依赖实测）和跨平台实测（Windows/macOS 都要真机验证）。

### 6. 结论

**可行，建议立项。** Tauri sidecar 模式与本项目"三进程 localhost"拓扑天然匹配：官方有专项指南、有同构先例、本项目无原生模块硬依赖（唯一 `.node` 来自 TUI，headless 用不到）。真正的工作量不在 Tauri 本身，而在三条线：①载荷瘦身（1.9GB → 目标 <400MB）②首启引导移植（bash+curl → 安装包内自动化）③跨平台签名分发。

路线选择：**方案 A（随包 Node 运行时）打首版**，方案 B（SEA）留作体积与源码保护的后备优化。沙箱与持久化是两个独立的产品决策（见风险 1/2），不阻塞本需求；其中沙箱与需求二（自研沙箱系统）有天然的先后协同关系——桌面版先"无沙箱可用"，自研沙箱落地后升级为"内置沙箱"。

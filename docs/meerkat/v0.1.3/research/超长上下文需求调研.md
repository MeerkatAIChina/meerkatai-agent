# 超长上下文的需求调研

## 目标

联调本地 QM 与服务器上部署的 `Meerkat-TRIZ-v1` 模型，实现**更长的上下文对话**，具体诉求：QM 能一次性输出长达 10 万字的文档。

## 服务器与硬件现状

| 项 | 值 |
| --- | --- |
| 主机 | `spark-f5a5`（Ubuntu 24.04，aarch64 ARM） |
| 硬件 | NVIDIA GB10（DGX Spark 规格，CUDA 13.0，驱动 580.82） |
| 内存 | 121 GiB 统一内存（CPU/GPU 共享，已用 110G，仅剩约 11G） |
| GPU 占用 | vLLM EngineCore 已占 97.5 GiB |

## 模型部署结构（关键）

`Meerkat-TRIZ-v1` 并非独立大模型，而是**挂在 Qwen3.6-35B-A3B 上的一个 LoRA 适配器**：

```
基础模型  Qwen3.6-35B-A3B-NVFP4-Fast   （MoE，35B 参数 / 激活 3B）
   └─ LoRA 适配  Meerkat-TRIZ-v1        （r=64，169MB，叠加在 base 之上）
```

- base 模型：`Qwen3.6-35B-A3B`，NVFP4 量化（FP8 激活 + 4bit 权重混合精度）；
- LoRA 适配器 `Meerkat-TRIZ-v1` 挂载于 `/models/adapter`，`base_model_name_or_path = Qwen/Qwen3.6-35B-A3B`。

## 当前 vLLM 启动参数

```bash
vllm serve /models/base
  --served-model-name Qwen3.6-35B-A3B-NVFP4-Fast
  --max-model-len 262144                 # 已开 256K 上下文
  --gpu-memory-utilization 0.83
  --max-num-batched-tokens 8192
  --max-num-seqs 64
  --dtype float16
  --enable-lora --lora-modules Meerkat-TRIZ-v1=/models/adapter --max-lora-rank 64
  --override-generation-config {"max_new_tokens": 16384, ...}   # 单次输出上限 16K
```

## 结论与瓶颈

**上下文长度不是瓶颈，单次输出上限才是。**

- `--max-model-len` 已是 262144（256K），base 模型原生支持 262K、YaRN 可扩到 1M——上下文空间充足。
- 真正的卡点是 `max_new_tokens: 16384`（≈1.2 万字），远超目标 10 万字（≈13~15 万 token）。

## 可行性边界

| 目标 | 需要 max_new_tokens | 能否达到 |
| --- | --- | --- |
| 现状（约 1.2 万字） | 16384 | 已实现 |
| 约 3 万字 | ~43000 | 可调参数达到 |
| 约 6 万字 | 81920 | 模型输出硬顶（官方 max output = 81920 token） |
| **10 万字** | ~150000 | ❌ 单次输出越不过模型 81920 输出硬顶 |

两条硬约束：

1. **模型输出硬顶**：Qwen3.6 官方 `max output = 81920 token ≈ 6 万字`，改参数无法突破。
2. **显存紧张**：121G 已用 110G（vLLM 占 97.5G），加大输出/上下文会进一步挤压显存。

## 可选方案

| 方案 | 能否到 10 万字 | 说明 |
| --- | --- | --- |
| ① 调大 `max_new_tokens` 至 81920 | 到 6 万字（模型上限） | 改启动参数 + 重启容器，最直接 |
| ② QM 分段生成后拼接 | 可以到 10 万字 | agent 分段写、再拼接，绕过单次输出上限 |
| ③ 换输出上限更高的 base 模型 | 可以 | 非改参数可解，需换模型 |

# 需求调研文档

> 针对《qm 二开调研.md》的三块需求（双模型路由矩阵、业务领域 Skills 包、插拔式二开），
> 对 qm 代码库四个关键问题的调研结果。结论基于当前工作区代码（2026-08-07）。

## 一、模型层：双模型可行性 —— 已原生支持，零内核改动

### 关键文件

- `src/model/pi-models.ts` — 内置模型注册表（Claude / GPT / OpenRouter），`resolveModel()` 统一解析入口
- `src/model/custom-providers.ts` — **自定义模型 provider 注册机制**
- `src/model/model-catalog.ts` — 模型目录（内置 + 自定义 + OpenRouter 动态拉取）
- `src/model/provider-endpoints.ts` — provider base URL 覆盖（单一收口点）

### 结论

qm 已支持管理员注册**自定义模型 provider**：只要服务端讲 OpenAI-compatible 或
Anthropic-compatible 协议，提供 baseUrl + API key + 模型 id 即可注册，注册后与内置模型
一样进入目录、一样被 pi harness 调用，密钥存加密存储。

**Meerkat-TRIZ-v1 的接入路径**：用 vLLM / Ollama / TGI 把模型以 OpenAI-compatible
端点暴露在内网，然后在 qm 管理后台注册为 custom provider。**不需要改任何内核代码。**

注意点：

- 自定义模型仅对 `pi` / `opencode` / `mock` harness 可用（`modelSupportedByHarness`），
  claude / codex harness 不认。部署时需确认 Agent 跑的 harness。
- `src/model/model-gateway.ts` 只是个内存审计环形缓冲，不是路由层，名字有误导性。

## 二、数据分级 × 路由矩阵 —— 部分有抓手，核心逻辑需新建

### 2.1 模型选择的收口点（路由矩阵的挂载位置）

`src/harness/harness-router.ts`：

- 每个 turn 都会过 `resolve(input) => RuntimeChoice{harnessId, modelId}`，
  由 `wiring.ts:782` 装配，当前实现是 `resolveRuntimeChoiceDurable`：
  **组织级默认 → 会话级覆盖 → 单次请求覆盖**，再校验 harness 白名单。
- `createHarnessRouter` 按 turn 路由到具体 harness adapter。

**这是全系统唯一"每个请求决定用哪个模型"的收口点**——路由矩阵的正确挂载位置。
但目前的选择依据只有配置（组织默认、会话覆盖、用户指定），**没有基于内容的路由**。

### 2.2 现有 classify 不是数据分级

`src/classify/scope-classifier.ts` 是给记忆条目打 scope 标签（session/org）用的，
和数据敏感度无关，不可复用。L1/L2/L3 分级是新概念。

### 2.3 可借鉴的现成机制

| 机制 | 位置 | 与需求的关联 |
| --- | --- | --- |
| Security Screener | `src/security/security-screener.ts` | HTTP 外部分类服务，在 `user_input` / `tool_response` 两个 hook 打分，verdict auto/strict，编排器消费结果。**敏感度分级服务可以照这个模式做**（自己起一个分级 endpoint） |
| Provider base URL 覆盖 | `src/model/provider-endpoints.ts` | `ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL` 等环境变量可把某个 provider 的全部请求指向任意 URL。**脱敏代理可以零内核改动插入**：部署一个本地脱敏网关，把通用模型 provider 的 baseUrl 指向它，由它脱敏后转发真实 API |
| Egress Proxy | `deploy/egress-proxy/`（Envoy + `src/egress-authz-main.ts`） | 网络层 fail-closed 出向管控，按 turn 发 capability token。可作为"L1 数据绝不到达通用模型端点"的**纵深防御兜底** |
| Tool Approvals | `src/deployment/deployment-layer.ts` 的 `ToolApproval`（require_approval / deny） | 工具级审批流已有先例，L2"提醒用户确认"可以镜像这个交互模式 |
| Secret Masking | `src/security/secret-masking.ts` | 只掩码环境变量里的凭据，不是业务数据脱敏，但模式可参考 |

### 2.4 缺口

1. **敏感度分级器**：新建。建议做成独立 HTTP 服务（复用 security-screener 的
   proxy 模式），输入用户消息/工具结果，输出 L1/L2/L3。
2. **内容路由**：新建。在 harness-router 的 resolve 收口点，根据分级结果选模型：
   - L3 → 通用模型（直通过）
   - L2 → 通用模型，但先走用户确认（镜像 ToolApproval 交互）
   - L1 → 强制 Meerkat-TRIZ-v1（本地）
3. **业务数据脱敏**：新建脱敏代理服务（部署层组件），配合 baseUrl 覆盖零内核接入。
4. **内核改动不可避免的部分**：(2) 的 resolve 装配在 `wiring.ts`（core）。
   最小化方案：给上游提一个"路由钩子"的 seam（如环境变量配置的策略模块路径），
   走 `upstream-pr` 流程回馈上游，fork 侧只在 layer 里放策略实现。

## 三、Skills 领域包 —— 插拔机制完善，零内核改动

### 机制

- `src/skills/skill-store.ts`：Skill 持久化存储，HMAC 签名清单，
  生命周期 draft → reviewed → published → archived；**按 scope 分层**（org/team/session），
  窄 scope 同名 skill 遮蔽宽 scope（shadowing）。
- 种子安装（`src/skills/seed.ts` + `wiring.ts:498-515`）：启动时从三个来源 upsert：
  1. `skills-seed/`（`SKILLS_SEED_DIR`，上游内置——**core，别动**）
  2. `plugins/*/skills/`（`PLUGIN_SKILLS_DIRS`）
  3. **deployment layer 的 `skills/` 目录**（`DEPLOYMENT_LAYER` 指向 `deploy/layers/<org>`）
- 命中机制：每个 turn，编排器把可见 skills 渲染成 `## Skills` 索引
  （`名称 — 描述 → 路径`）注入系统提示（`src/skills/materialize.ts:skillsIndex`，
  `src/core/orchestrator.ts:862`），Agent 读 SKILL.md 按步骤执行。

### 结论

TRIZ 验证、概念设计、市场预估、卖点分析、电商文案等领域包，写成标准
`SKILL.md` + 附属文件，放进 `deploy/layers/<org>/skills/<name>/` 即可随启动安装、
随内容变更更新，**完全不动内核，且天然属于 fork 私有领地**。

**命中准确性的关键**：索引里只有 name + description 一行。要避免幻觉命中/漏命中，
description 必须写清"什么时候用、什么时候不用"（触发词、反例）。
另外可以配合同名 shadowing：组织层 skill 可以遮蔽上游同名 skill，便于定制覆盖。

## 四、定制边界 —— fork 规则已经替你划好了

| 位置 | 性质 | 放什么 |
| --- | --- | --- |
| `deploy/layers/<org>/` | **fork 私有，永不回上游** | 部署配置、`skills/`（领域包）、`sandbox/`（组织工具）、`plugins/<name>/`（组织专属服务镜像）、`infra/` |
| `plugins/`（admin/auth/chassis/portal/web-ui/onboarding） | **core**，与上游字节一致 | 不要放组织定制 |
| `skills-seed/` | **core** | 不要放组织 skill |
| `src/` | **core** | 改了就破坏跟随升级；必要改动走 `upstream-pr` 回馈上游 |
| `deploy/layers/<org>/skills/` | layer 内 | **领域 Skills 包的家** |

同步上游用 `update-qm` skill（merge，不 rebase）；`upstream-pr` skill 会把通用改动
送回上游且不泄露组织上下文。

## 五、总体评估与建议路线

| 需求 | 内核改动 | 落地位置 |
| --- | --- | --- |
| 双模型并存（接入 Meerkat-TRIZ-v1） | **无** | 内网推理服务 + custom provider 注册（管理后台配置） |
| 业务领域 Skills 包 | **无** | `deploy/layers/<org>/skills/` |
| 脱敏代理（L3/L2 出向脱敏） | **无** | layer 内部署脱敏网关 + `*_BASE_URL` 覆盖 |
| L1 硬隔离兜底 | **无**（复用 egress-proxy） | layer 部署配置 |
| 敏感度分级器 | **无**（独立服务） | layer 内新服务，参照 security-screener 协议 |
| **内容路由矩阵 + L2 确认交互** | **有（最小化）** | 给上游提 routing-hook seam（`upstream-pr`），策略实现放 layer |

建议优先级：先做零改动的四件（接模型、写 Skills、脱敏代理、egress 兜底），
把"路由矩阵"的内核 seam 设计成可上游化的通用能力（按内容标签选模型），
这样既满足插拔要求，又不让 fork 背上维护私有内核补丁的负担。

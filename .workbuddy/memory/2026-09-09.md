## YaRN 1M 二次深挖（SSH 直取 config.json，纠正关键认知）

- **纠正 ①（重要）**：KV cache **已经是 fp8**！`/models/base/config.json` 的 `quantization_config.kv_cache_scheme.num_bits=8`。故 1M 的 KV cache 约 **10.1GB**（非 fp16 的 20GB），当前 256K 约 2.5GB，**增量仅 ~+7.6GB**（vs 之前误估 +15G）。30 层 DeltaNet 是 O(1) 状态，不吃 KV cache，所以只有 10/40 层随上下文增长。
- **纠正 ②（重要）**：模型是 **mRoPE（3D 位置编码）**，`text_config.rope_parameters` 实值：`mrope_interleaved:true`、`mrope_section:[11,11,10]`、`partial_rotary_factor:0.25`、`rope_theta:10000000`、`rope_type:"default"`。启用 YaRN 时 **`mrope_section`/`mrope_interleaved` 必须保留**，不能只照抄 Qwen3-Next 的 `--rope-scaling`（那是 `qwen3_next` 路径）。
- **官方正确写法（Qwen3.5/3.6 = qwen3_5_moe）**：`VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` + `--hf-overrides '{"text_config":{"rope_parameters":{...,"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":262144}}}'` + `--max-model-len 1010000`。已从 Qwen3.5-122B-A10B/397B-A17B 官方模型卡交叉确认。
- **qm 侧易漏层**：`custom_model_providers` 表实测 `meerkat-vllm` 两个模型 `contextWindow=262144 / maxTokens=8192`。pi-harness 有 output-budget guard，按 `contextWindow - prompt - 安全余量` 钳 max_tokens → **vLLM 扩到 1M 后 qm 侧 contextWindow 也必须改 1010000**，否则输出仍被钳在 256K 内。
- LoRA（r=64）只改投影权重不改 RoPE，与 YaRN 正交，**无需重训**；但 >256K 效果需 RULER 实测。
- 静态 YaRN 副作用：短文本(<256K)轻微掉点；"10万字输出"≈150K tokens 本身在原生 256K 内，其实不需要 YaRN，只需放开输出上限。
- 产出：`docs/meerkat/v0.1.3/YaRN扩展可行性调研.md`（完整报告，含分层改法清单）。

## 同事观点 review（1M 显存可行性纠偏）

- 同事三点观点，review 结论：方向大多对，但「1M 远超 128GB 显存不可行」这句**是错的**。
- **关键结论（纠正认知）**：1M 上下文的 KV cache 本体仅 ~10GB（fp8，仅 10 层全注意力吃 KV，30 层 DeltaNet 不吃）。128GB 统一内存**装得下 1M 本身**。真正的瓶颈是「并发 × 上下文」的乘积——高并发（16）× 256K 时 KV 池 ~40GB 撑不住；降到低并发（1-2 路）时 1M 完全可行。所以「降并发」既是同事观点 1 的解法、也是观点 2「不可行」的反例。
- 同事工程参数（同事在我调研后已调）：`gpu-memory-utilization` 实际 **0.6** + **8 并发**（我之前实测是 0.83，数值出入是同事后调的，非冲突）。
- 术语纠偏：Qwen3.6 线性层是 **Gated DeltaNet**（不是 Mamba）；max-model-len 官方目标是 **1010000**（不是 1048576，那是 262144×4 的纯数学值）。
- YaRN 只对全注意力层的 RoPE 生效，DeltaNet 无 RoPE 不受影响——这是架构事实（中性偏利好）；真实风险是「DeltaNet 长文外推数值稳定性未验证」，YaRN 管不到这一块。

## qm 侧 contextWindow 改法调研（服务器 qm-shao 部署）

- **服务器 qm-shao 拓扑**：`qm-shao-portal`(host 8081, IAP) + `qm-shao-web-ui` + `qm-shao-core`(host 8080) + `qm-shao-pg`(postgres, db=qm) + vllm，**无 admin 容器（无治理台）**。portal 只反代 web-ui（`WEB_UI_UPSTREAM=http://web-ui:8080`），无 admin upstream。
- **contextWindow 存两份**：DB `custom_model_providers.json`（jsonb，`models[].contextWindow`）+ 进程内存 registry（`setCustomProviders` 加载）。pi-harness 从**内存**读，所以**只改 DB 不生效**，必须走 admin API（upsert + `refreshCustomProviders`）或重启 core。
- **core admin API 认证链路（已实测 GET 200 走通）**：需要两层——① source-auth 签名：`x-signature = "v0="+HMAC-SHA256(CORE_SIGNING_SECRET, "v0:{ts}:{METHOD}\n{path}\n{body}")` + `x-timestamp`；② portal identity JWT（HS256，用 `PORTAL_IDENTITY_SECRET`，header `{alg:HS256, kid:sha256(secret)base64url[:8]}`，claims `{p:"admin-alice", exp:now+60s(ms)}`）放 `x-portal-identity` 头。两个 secret 都在 core 容器 env（`CORE_SIGNING_SECRET`/`PORTAL_IDENTITY_SECRET`）。admin actor=`admin-alice`（`admin_grants` 表 `org:shao`/`org_admin`）。
- 改法：`PUT http://localhost:8080/v1/admin/custom-providers/meerkat-vllm`，body 带 name/protocol/baseUrl + models（contextWindow 改 1010000），**不传 apiKey**（保留原加密 key）。
- **admin 后台 UI**（`plugins/admin/public/index.html`）有 Custom providers 编辑界面，models 输入格式每行 `id | name | contextWindow | maxTokens`（`|` 分隔）。但本部署无 admin 容器，用不了。
- web-ui 里的 custom provider（pi-web-ui `CustomProviderDialog`/`ProvidersModelsTab`）是**本地配置**（API key 存浏览器 localStorage，type=ollama/vllm/lmstudio），**不是** qm core 的 org 级 provider，两者不是一回事。
- durable-map 缓存机制：`CACHE_MAX_AGE_MS=15000`，`snapshot()` 有 15 秒缓存 + version 校验；`get()` 直查 DB。
